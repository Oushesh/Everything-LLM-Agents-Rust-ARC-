## Goal
   The goal of this repo is to build a Policy Based Agent capable of doing different levels of autonomy tasks.
   The Key Idea is to always use one agent to score multiple solutions generated by one agent and another agent to score them and the best fit and the second agent can be given skills on what basis or merit it can actually score or evaluate the initial decision or conclusion reached in the first place


## Folder Structure: 
   How to layer or build this System? 

   We can think of this problem within layers.


   Layer 0: None - DBA does everything (Example: Manual scripts)


   Layer 1: Ground Truth RAG  - Preventing Hallucination at the source 

   How to solve this? Grounding.
   In theory if you have examples of those code or how its done you can write guidelines in (.md) files for the agent to refer to.


   In this case particulary, LLMs hallucinate. In DBA context, hallucinated SQL syntax can corrupt data or crash databases. We solve this at knowledge layer.

   For example for the oracle system we add all the skills under the folder docs/oracle directory contains verified oracle syntax documentation.

    ```
    ~/.../docs/oracle/
    ├── tablespace_management.md      # Verified ALTER TABLESPACE syntax
    ├── session_management.md         # KILL SESSION, blocking resolution
    ├── storage_clauses.md            # AUTOEXTEND, MAXSIZE, etc.
    ├── performance_views.md          # V$ and DBA_ view definitions
    └── version_compatibility.md      # 11g vs 12c vs 19c differences    
    ```

    Above all those data or knowlege base comes from domain experts which write them.


   We enhance knowledge with current Instructions since LLM training data without the Knowledge base (.md) files to ground itself might refer to outdated syntax, deprecated features and version-specific quirks.

   Why this matters: 

   * LLM training data includes outdated syntax, deprecated features and version-specific quirks.

   * RAG retrieval ensures generated SQL matches your actual Oracle version or whatever version or Postgresql. 


    * Knowledge base has to be versioned like GIT and auditable - you know exactly what LLM "knows"


    Another strong feature - The argue/select or decision making pattern from this RAG corpus: when an agent generates multiple fix candidates, each candidate's SQL is validated agaisnt ground truth before scoring.

   Layer 2: Policy Files(.md) - Domain Experts define Boundaries. 

   The entire system behavior is defined in markdown files that DBAs can edit without writing code:
